Status roboczy 2026-09-09. Źródło zgłoszenia: Huawei P30 Pro VOG-L29, Android 10,
EMUI 11, standardowa wielkość tekstu. Obecna dystrybucja: 1.0.0 (50), test wewnętrzny.
Publiczna publikacja nie została zlecona w tej fali.

## Warunki takie jak iOS

Odczyt API App Store Connect z 9 września potwierdził 175 terytoriów, bez odchylenia
od konfiguracji repo. Oba produkty iOS mają stan READY_TO_SUBMIT; to nie jest dowód
akceptacji do publicznej sprzedaży przez Apple.

| Plan | Polska | USA | Bezpłatny okres dla uprawnionego nowego klienta |
|---|---:|---:|---:|
| PRO miesięczny | 14,99 zł / miesiąc | 3,99 USD / miesiąc | 7 dni |
| PRO roczny | 119,99 zł / rok | 31,99 USD / rok | 14 dni |

To samo PRO, te same funkcje i to samo konto Strength Save na iOS/Android/web.
Roczny plan jest opłacany za cały rok; cena przeliczona na miesiąc jest tylko
porównaniem. Cena i dostępny trial w aplikacji pochodzą z odpowiedzi sklepu,
a kupowana opcja Android jest dokładnie tą pokazaną użytkownikowi.

- Instalacja ani rejestracja nie pobiera pieniędzy i nie zaczyna automatycznie triala.
- Trial zaczyna się po świadomym potwierdzeniu oferty w oknie Google Play.
- Przy trialu pierwsze cykliczne obciążenie następuje po 7 albo 14 dniach, chyba że
  klient wcześniej anuluje. Bez uprawnienia do triala sklep pobiera opłatę przy zakupie.
- Subskrypcja automatycznie odnawia się co miesiąc albo rok. Usunięcie aplikacji nie
  anuluje subskrypcji. Zarządzanie prowadzi do sklepu, w którym dokonano zakupu.
- Warunki zaplanowane na Androidzie ograniczają ofertę do osoby, która nie miała
  wcześniej żadnej subskrypcji w tej aplikacji, aby nie dawać kolejnych triali po
  przejściu między miesięcznym i rocznym planem. Apple stosuje własną kwalifikację
  do oferty w grupie subskrypcji; konta sklepów nie współdzielą historii triali.
- Ostateczna kwota i data pierwszego obciążenia są pokazane w systemowym oknie
  zakupu. Dla wspólnych walut skrypt kopiuje ceny detaliczne iOS; gdzie Google używa
  innej waluty, przygotowuje osobno raport przeliczenia Google z tej samej ceny USD.

Podstawa: [Google — subskrypcje](https://support.google.com/googleplay/android-developer/answer/140504?hl=en),
[Google — cykl subskrypcji](https://developer.android.com/google/play/billing/lifecycle/subscriptions),
[Google — kwalifikacja ofert](https://developers.google.com/android-publisher/api-ref/rest/v3/monetization.subscriptions.basePlans.offers).
Dowód konfiguracji iOS: [ios-billing-reference.json](../audit/android-2026-09-09/ios-billing-reference.json).

## Rzeczywista blokada Google Play

API zwróciło HTTP 400 FAILED_PRECONDITION:
`Cannot create a subscription without first registering a payments profile for the developer account.`

Właściciel musi otworzyć **Google Play Console → Ustawienia → Profil płatności**
i utworzyć profil sprzedawcy, podając rzeczywiste dane firmy i wymagane dane do
rozliczeń. Tych deklaracji i danych nie da się zgadnąć ani zastąpić skryptem API.
Nie jest to ponowna konfiguracja service account — dostęp API już działa.

Po zakończeniu profilu można przygotować i przejrzeć dokładny plan przez:

```sh
uv run scripts/google_play_subscriptions.py --output /tmp/strength-play-billing-plan.json
```

Zastosowanie uzgodnionych warunków:

```sh
uv run scripts/google_play_subscriptions.py --output /tmp/strength-play-billing-applied.json --apply
```

Skrypt tworzy brakujące produkty/base plans/oferty, sprawdza ceny i trial, dopiero
potem aktywuje i czyta wynik. Odmawia nadpisania istniejącej innej ceny/oferty.
Na dziś nie wykonano udanej aktywacji: profil sprzedawcy jest warunkiem koniecznym.
[Testy skryptu](../scripts/test_google_play_subscriptions.py) obejmują parytet,
kwalifikację triala i zatrzymanie przy błędnym profilu/istniejącej innej cenie.
[Dowód blokady API](../audit/android-2026-09-09/play-billing-precondition.json).

RevenueCat Android `appe7c441de60` ma podłączone credentials; oba produkty Google
są przypięte do `pro` oraz `default/$rc_monthly` i `default/$rc_annual`, tak jak Apple.
[Odczyt mapowań](../audit/android-2026-09-09/revenuecat-mappings.json).
API konfiguracji poprawiono: oficjalny typ aplikacji to `play_store`; starszy
skrypt szukał wyłącznie `google_play` i nie rozpoznałby prawidłowo utworzonej aplikacji.

## Test zakupu i pozostałe bramki sklepu

Konto `greg2026greg@gmail.com` jest testerem instalacji. Nie ma jeszcze dowodu,
że jest też testerem licencji. **To dwa osobne ustawienia.** Przed zakupem dodaj
konto w **Google Play Console → Ustawienia → Testowanie licencji**. W oknie płatności
ma być wyraźny komunikat testowy i testowa metoda płatności. Sam test wewnętrzny
nie wyłącza prawdziwych opłat. W standardowym sandboxie trial trwa około 3 minut,
miesiąc około 5 minut, rok około 30 minut — to przyspieszenie testowe, a nie warunki
prawdziwego klienta. [Oficjalny przewodnik testów Google](https://developer.android.com/google/play/billing/test).

Należy przetestować zakup, odmowę, oczekiwanie, anulowanie przed końcem triala,
odnowienie, wygaśnięcie, przywrócenie i zmianę urządzenia/konta. Bez tego publiczny
launch płatności nie jest oznaczony jako gotowy.

Google RTDN pozostaje do połączenia i sprawdzenia: w RevenueCat Google App Settings
wybrać **Connect to Google**, a nazwę tematu wkleić w Play Console **Monetization setup
→ Real-time developer notifications**, zapisać i wysłać test. Pub/Sub API i wymagane
role są przygotowane; odczyt nie wykazał jeszcze tematu RevenueCat/Play. To przyspiesza
obsługę odnowień/zwrotów w backendzie. [Instrukcja dostawcy](https://www.revenuecat.com/docs/platform-resources/server-notifications/google-server-notifications).

Publiczna premiera wymaga również ukończenia listingu EN (ikona/screenshoty/opisy),
formularzy Data Safety, Health apps, odbiorców/ratingu, dostępu dla recenzenta oraz
weryfikacji publicznych Privacy/Terms/delete-account. Stan testu wewnętrznego nie
potwierdza ukończenia tych formularzy. W tej fali nie składano ich jako prawdziwych
bez sprawdzenia ani nie uruchomiono publicznej ścieżki produkcyjnej.
